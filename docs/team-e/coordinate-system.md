# 座標変換パイプライン

- ここでは、星表に書かれた数字をグラスの196×196画素のどこに点を打つかに変換するための仕様を決めるドキュメントである
- 星表に載っているのは「シリウスは赤経 6h45m、赤緯 −16.7°」といったデータだが、一方でグラスに出したいのは「画面の (x, y) = (120, 47) に明るい点を打つ」という情報
- この間には次の4種類の基準の違いがある

1. 星表は2000年基準・現在は2026年
2. 地球の時点（同じ星でも時刻絵見える方向が変わる）
3. 観測値が違う（鯖江とシドニーでは同じ星が正反対の方向に見える）
4. 頭の向きが違う（同じ空でもどこを向いているかで画面に入るものが変わる）

- **`要決定` `要確認` の付いた項目はまだ決まっていない**

## 全体の構成

```
SABERA ──── 六軸センサ（加速度＋ジャイロ）────→ スマホ
   ↑                                              │
   │                                              │ 日時・時期・位置（GPS）
   │                                              │ 星座データベース
   │                                              │ 磁気センサー
   │                                              │ 恒星・月キャリブレーション
   │                                              ↓
   └──── 画像送信（196x196 グレースケール）──── 天球描画 → 切り抜き

SABERA ──── 横をタップ（gestureEvents）────→ AI 発火 → 音声で解説
```

- **グラスは表示とセンサーに徹し、計算はすべてスマホ側**
- グラスへ送るのは画像のみ

## 変換の全体像

- 変換の全体像は以下の通り

```
星表（ICRS / J2000.0 赤経・赤緯）
        ↓ ① 歳差
of-date の赤道座標 (α, δ)
        ↓ ② 恒星時 — 観測地の経度 + UTC → LST、時角 H = LST − α
時角系
        ↓ ③ 地平座標変換 — 観測地の緯度 φ
地平座標（方位角 A・高度 h）※ 真北基準
        ↓ ④ 姿勢 — グラスの六軸 + 方位オフセット（キャリブレーションで決める）
視線ベクトル
        ↓ ⑤ 投影 — 視線中心の接平面へ
196x196 のスクリーン座標
        ↓ ⑥ ラスタライズ（グレースケール 0-255）
sendImage(width, height, grayscale)   ※ 量子化と圧縮は SDK 0.0.12 が行う
```

- 「星表の座標」と「of-dateの赤道座標」に関しては、1回計算すれば当分変わらない
- 「地平座標」は時刻とともに変わる、「視線ベクトル」への変換は毎フレーム変わる
- この頻度の違いが「行列を毎フレーム組み直さない」という方針につながる

## 実装方針（全段共通）

### 内部表現は単位ベクトルで統一する

- 素直に実装すると、各段を「角度→角度」の変換として書きたくなる（例：赤経赤緯を入れて方位角高度が出てくる関数）
- しかしこれには2つの罠がある
1. 天頂（高度90度）では方位角が定義できない
2. $¥cos{h}$での除算ができない場合がある（特に90度の時）
- **そこで角度ではなく単位ベクトルで持つ**
- このようにすることで、変換がすべて3×3の回転行列の掛け算になる
- ①〜④ がすべて回転行列の積になり、特異点が消える

```
v_screen = R_attitude · R_horizon(φ) · R_hourangle(H) · R_precession · v_catalog
```

- 歳差 = `R_z(−z) · R_y(θ) · R_z(−ζ)`
- 時角 = `R_z(H)`
- 赤道→地平 = 緯度 φ による `R_y`
- 姿勢 = グラスの回転行列（六軸から得る）

- さらに、もう1つの利点として行列を先に掛け合わせておけるという利点がある
- 歳差行列は起動時に1回作ればよく、緯度による行列は場所が変わるまで固定、毎フレーム変わるのは時角と姿勢だけなので、`R_precession` と `R_horizon` は事前に合成して 1 つの行列にしておける
- 5000 個の星を毎フレーム変換するときに重要

### 座標系の規約を 1 箇所に固定する

**符号バグの温床。** 決めて文書に書き、実装では 1 箇所に定数として置く。

| 決めること | 採用（案） | 備考 |
|---|---|---|
| world 座標系 | **ENU**（X=東, Y=北, Z=天頂） | Android の `getRotationMatrix` と同じ。NED と混ぜない |
| 方位角の起点 | **北 = 0°** | 天文の伝統には南起点の流儀もある。混在させない |
| 方位角の向き | **東回り（時計回り）** | Android と同じ |
| 手系 | **右手系** | |
| グラス機体座標 | `要確認` | どの軸が前方・上方か。API 解放時に確認 |

### 時系は UTC で足りる

- `GMST` の式は **UT1** 基準だが、`DUT1` は最大 0.9 秒 = **約 13″**。無視できる
- 歳差の計算は本来 **TT**（TT − UTC ≒ 69 秒）だが、歳差量への影響は無視できる
- → **UTC をそのまま使ってよい。** ただし端末時計のずれは別問題（1 分ずれで 0.25°）

### ユリウス日は D を直接持つ

- `JD ≒ 2,460,000` を Double で持つと仮数部の上位が食われる
- **`D = JD − 2451545.0` を直接計算して保持する。** 大きな数の引き算を避ける

### 日周運動の速さ

- 星は **15″/秒**（1 分で 0.25°、4 分で 1°）
- **画像の更新間隔がこれを超えると、静止して見えない／ずれる**
- 転送時間の実測（後述）と合わせて更新方針を決める

## ① 星表 → of-date

- 地球の自転軸は約26000年周期でコマのように首を振っている
- これにより天の北極の位置が動き、赤経赤緯の原点そのものがゆっくりずれていく
- J2000から2026年までの26年で約0.36度
- これは満月の直径に近い量なので、無視してしまうと星座線が明らかにずれてしまう
- そこで**歳差行列を導入する**
- ここで無視しているのは、オーダーが明らかに小さい以下の3つ
1. **章動**（最大 17″）
2. **固有運動**（26 年で数十″）
3. **光行差**（最大 20″）

## ② 恒星時

- 地球が回っているため、「今どの赤経が南中しているか」が時々刻々と変化する
- これを表すのが恒星時
```
GMST = 18.697375 + 24.065709824279 × D   （時間単位、D = JD − 2451545.0）
```
- 係数が 24 ではなく 24.0657 なのがポイント
- これは恒星日が太陽日より約 4 分短いことを表している（地球は自転しながら公転もしているので、太陽に対して 1 周する間に星に対しては 1 周と少し回る）

- `LST = GMST + 経度 / 15`（東経を正）
- 時角 `H = LST − α`

## ③ 地平座標変換

- 天の北極・天頂・星の3点が作る球面三角形に球面の予言定理を導入する

観測地の緯度 φ、時角 H、赤緯 δ から：

```
sin h = sin φ · sin δ + cos φ · cos δ · cos H
A = atan2( −cos δ · sin H,  sin δ · cos φ − cos δ · sin φ · cos H )
```

- `A` は**真北基準・東回り**
- **大気差** — 高度 0° で約 34′、10° で約 5′、45° で約 1′。地平線近く以外は無視できる

## ④ 姿勢の出所

- **ここから先がデバイス固有の問題**
- **グラスは六軸センサ（加速度＋ジャイロ）。** ここから何が言えるかが設計を決める。

### 六軸で取れるもの・取れないもの

| 量 | 可否 | 理由 |
|---|---|---|
| **pitch・roll** | **絶対値が取れる** | 加速度計が重力を測るため |
| **yaw** | **絶対値が取れない** | 磁力計が無く、ヨー方向には基準になる外力が無い |
| 方位の**変化量** | 取れる（ただしドリフトする） | ジャイロの積分 |

- **グラスに磁力計が無い以上、グラスの絶対方位を直接得る手段は存在しない**
- 未知数は **方位オフセット 1 つだけ**
- これをキャリブレーションで決める

### スマホの磁気センサーでは代替できない

- スマホの磁気が示すのは**スマホの方位**であって、**グラスの方位ではない**
- 頭とスマホは独立に動くので、両者の相対姿勢は未知
- → 磁気とジャイロを相補フィルタで融合する定石が、**そのままでは使えない**

スマホの磁気の使い道は次に限られる：

- キャリブレーション対象の天体をユーザーに案内するための**初期推定**（「右のほうにベガがあります」）
- その場の**磁気偏角・局所異常の把握**（`GeomagneticField.getDeclination()`）

`要決定` 磁気を初期推定として使うか、最初から天体アライメントだけで進めるか

## キャリブレーション設計

- **このアプリの精度を決める中核**

### 一星アライメントで足りる

- 一般に、経緯台では2つの星を導入して行う
- これは架台の水平が出ていないからで、水平の傾き2自由度+方位1自由度=3つの未知数を解く必要があるため
- しかし、グラスの場合は加速度計がすでに水平を教えてくれる
- つまり残る未知数はYaw1つ
- したがって、天体1つで一意に定まる
- 手順は以下の通り

1. ユーザーに基準天体を視野中心に入れてもらう
2. その瞬間のグラスの姿勢（六軸から得た相対姿勢）を記録
3. その天体の真の方位・高度は時刻と位置から計算できる
4. 差分が方位オフセット

### 基準天体は低い高度を選ぶ

**アライメント誤差の伝播を考えると、基準天体の高度が効く。**

- 高度 h の天体では、天球上の角度ずれ δ に対して方位オフセットの誤差は `δ / cos h`
- そのオフセットで高度 h′ を見ると、天球上の誤差は `δ · cos h′ / cos h`
- → **高い天体で校正すると誤差が拡大し、低い天体で校正すると縮小する**

| 校正天体の高度 | 誤差の増幅（`1 / cos h`） |
|---|---|
| 20° | 1.06 倍 |
| 45° | 1.41 倍 |
| 60° | 2.0 倍 |
| 80° | **5.8 倍** |

- 純粋に誤差だけなら**低いほどよい**が、低すぎると大気差（高度 10° で 5′）と地形障害が効く
- **高度 20〜40° の天体を選ぶのが妥当**
- 仰角（pitch / roll）は重力基準で絶対値が取れているので、**解いているのはヨー 1 つだけ**である点は変わらない

### 月を使うなら地心視差の補正が必須

- **月の地平視差は最大約 57′（≒1°）**。観測地によって見える方向がずれる
- 恒星（視差ゼロ）と違い、**トポセントリック補正を入れないと 1° の系統誤差が乗る**
- 位置は GPS で分かるので計算はできる
- 月の位置は簡易式（Meeus の簡略版など）でも ±10′ 程度は出る。アライメント精度は度のオーダーなので十分

### `要決定` 基準天体の選ばせ方

- **前提：カメラが無いので、機械側は「本当にその天体を見ているか」を確認できない。** 完全にユーザーの申告に依存する。

| 候補 | 見つけやすさ | 精度上の注意 | 実装の重さ |
|---|---|---|---|
| **月** | **圧倒的に易しい** | 地心視差の補正が必須（最大 57′） | 簡易式で ±10′。軽い |
| 明るい惑星 | 易しい | 視差は無視できる | 軌道計算が要る。重い |
| 1 等星（21 個） | **どれか分からない** | 視差・固有運動とも無視できる。最も正確 | カタログを引くだけ。最軽量 |

**磁気センサーの使いどころはここ。** 精度を出すためではなく、**候補を絞るために使う**：

1. 磁気で ±15° の粗い方位を得る
2. その方向にある明るい天体をスマホ画面に出す
3. 「南南西・高度 30° にベガがあります。視野中心に入れてタップ」
4. ユーザーは候補から選ぶだけ

- **推奨（未決定）: 月が高度 20〜40° に出ているときは月**（視差補正込み）。それ以外は**磁気で絞った 1 等星から選ばせる**
- 惑星は軌道計算が重いので後回しでよい

### 校正結果の確認ステップ

- 機械側で校正の正否を確認できないので、**ユーザーに確認させる**必要がある
- 校正直後に星図を出し、「見えている空と合っていますか」と聞く
- ずれていればジェスチャー（`SINGLE_TAP` / `HOLD`）で微調整させる

### 本当の問題はドリフト率

- MEMS ジャイロのヨードリフトは、民生品だと**数°/分**のオーダーになることがある
- **1 回のアライメントがどれだけ持つかで体験が決まる**
- 数分持つなら「起動時に 1 回」で済む。数十秒なら常時再校正が要り、実用にならない
- `要確認` **実機でドリフト率を測る。これが最優先の実測項目**

### ドリフトが速い場合の逃げ道

このアプリは**タップした瞬間だけ精度が要る**（常時追従が要件ではない）。これを利用できる。

- 解説の直前にアライメントを挟む（「月を見てタップしてください」→ その姿勢を基準に描画）
- 連続追従を諦め、スナップショット方式にする
- アライメントを「精度を上げる追加機能」とし、まずは磁気なしの相対表示で成立させる

## ⑤ 投影

- 視線方向を中心とした接平面に投影する
- 中心からの角距離 θ を像面半径 r に写す
- 球面を平面に写す以上、**すべてを保つことは原理的に不可能**。何を諦めるかを選ぶ

### `要決定` 投影方式

| 方式 | 式 | イメージ | 保つもの |
|---|---|---|---|
| **心射図法（gnomonic / TAN）** | `r = tan θ` | 球の**中心**から光を出して接平面に落とす | **大円が直線になる** |
| **ステレオ投影（stereographic）** | `r = 2 tan(θ/2)` | 球の**反対側の極**から光を出す | **角度と形**（等角写像） |

形の歪み（縦横比の崩れ）を FOV ごとに比べると：

| FOV | gnomonic | stereographic |
|---|---|---|
| 40° | 6.4% | **0%** |
| 60° | 15.5% | **0%** |
| 90° | 41% | **0%** |

- gnomonic の歪みは `sec θ`（半径方向 `sec²θ`、接線方向 `sec θ` の異方性）
- stereographic は等角なので**形の歪みは常にゼロ**。全体のスケールだけ周辺で 3〜7% 変わる

判断材料：

- このアプリは**星座の「形」を見せて同定させる**のが本質 → 等角の stereographic が理屈では有利
- gnomonic の利点「星座線を直線で引ける」は、**円弧を 5° ごとの折れ線に分割すれば数行で済む**ため差は小さい
- 196x196 という解像度では差が視認できない可能性もある
- **推奨（未決定）: stereographic。** FOV を後から広げたくなったときにも耐える

### `要決定` FOV（画角）

- 196px に空の何度分を入れるか
- 狭いほど星が大きく描け、広いほど星座と周囲の文脈が入る。

空のサイズの目安：満月 0.5° / こぶし（腕を伸ばして）約 10° / **オリオン座 約 20°** / 北斗七星 約 25° / さそり座 約 40°

| FOV | 解像度 | 5 等まで視野内 | 入るもの |
|---|---|---|---|
| 20° | 9.8 px/度 | 15 個 | オリオン座がぎりぎり。星は大きく描ける |
| **30°** | 6.5 px/度 | 33 個 | 星座 1 つ＋周辺の文脈 |
| **40°** | 4.9 px/度 | 58 個 | 星座 1 つに余裕 |
| 60° | 3.3 px/度 | 129 個 | 星座 2〜3 個。密で潰れ気味 |

**前提が 1 つ未確認：** `要確認` グラスの表示画角（196px が視野の何度を占めるか）

- **視界に重ねる**なら FOV は表示画角に一致させる必要があり、**選ぶ余地がない**
- **参照図として見せる**なら自由に選べる
- **推奨（未決定）: 自由に選べる場合は 30〜40°。** オリオン座が画面の半分〜2/3 を占める大きさ

### `要決定` ロール（首の傾き）の扱い

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **追従** | グラスの傾きに合わせて星図も回す | 実際の空と一致する。重ねて見るなら自然 | 星図が常に回って読みにくい。文字を焼くと文字も傾く |
| **固定** | 地平線を常に水平に保つ | 星座早見盤と同じで参照図として読みやすい | 頭を傾けると視界とずれる |

- ロールは重力基準で**絶対値が取れている**ので、**どちらも実装できる**。純粋に体験の判断
- **推奨（未決定）: 地平線水平固定で始める。** 196x196 の小さな窓に出す以上、AR オーバーレイより参照図としての性格が強いと見込まれるため
- 投影段のパラメータにしておけば、実機で重なり具合を見てから切り替えられる

## ⑥ ラスタライズ

出力先は `sendImage`。**SDK 0.0.12 で簡素化され、取り込み済み。**

```kotlin
fun sendImage(width: Int, height: Int, grayscale: ByteArray)
```

- 渡すのは **1 画素 1 バイトのグレースケール**（0-255、左上から行優先、長さは `width * height` 以上）
- **3bit への量子化と RLE 圧縮は SDK が行う。エンコーダを自前で書く必要はない**
- サイズ上限は **196x196**。超えるとファーム側で弾かれ、何も表示されない
- `samples/kmp/app/.../GlassImage.kt` に流用できるものがある
  - `Bitmap.toGlassGrayscale()` — 縦横比を保って 196 に縮小し、輝度だけ取り出す
  - `testPatternImage()` — 画像を用意せず送信を試せるテストパターン
- `samples/kmp/app/.../ImageScreen.kt` に送信画面のサンプルがある。**転送時間の実測はここから始められる**

残る設計判断：

- `要決定` 星の等級の表現。グラスは 3bit（8 階調）で、**量子化は SDK が行うので制御できない**。明るさだけでは潰れるので、点の大きさ（1px / 2px / 3px）との組み合わせを検討する
- 描くのは 0-255 のグレースケールでよいので、**Android の Canvas でそのまま描いて `toGlassGrayscale()` に通す**のが素直
- `要決定` 星座線を描くか、線の階調をどうするか
- `要決定` 星座名を画像に焼くか、テキストページに出すか（**画像とテキストは同時に出せない**。ページ遷移が要る）

| `data/stars.6.json` | 641 KB | 6 等までの恒星 **5,044 個** |
| `data/constellations.lines.json` | 26 KB | 星座線。**89 グループ / 150 本の折れ線 / 893 頂点** |
| `data/starnames.json` | 664 KB | 固有名・バイエル符号など（必要なら） |

- 形式は **GeoJSON**。`id` は **Hipparcos 番号**、`properties` に `mag`（実視等級）と `bv`（B−V 色指数）
- 元期は **J2000 を実測で確認済み**（シリウス 0.7″、ポラリス 1.8″ の差＝丸め誤差の範囲）
- 出典は XHIP（Extended Hipparcos Compilation）ほか。VizieR 由来

**座標の持ち方に注意：**

- 座標は `[lon, lat]` で、**`lon` は −180〜180 に折り返されている**（赤経ではない）
- 赤経に戻すには `RA = lon < 0 ? lon + 360 : lon`
- `lat` はそのまま赤緯

### ライセンスの比較

- `要決定` d3-celestial を採用するか

### まだ足りないもの

- `要決定` **星座の日本語名**。d3-celestial は IAU 略号（`And` `Ori` …）と英名。和名の対応表は別途用意する
- 星座境界（`constellations.borders.json`）は同梱にあるが、**星座線があれば同定には足りる**ので優先度は低い

## 音声解説の経路

**SDK に音を鳴らす API が無い。**

- `openGlassMic()` / `closeGlassMic()` / `GlassClient.micChannel` は**入力のみ**
- 公開 API に音声出力・再生・音量に関するものは存在しない
- `要確認` 「AI 発火 → 音声で解説」の音がどこから出るのか
  - グラスが Bluetooth オーディオ（A2DP / HFP）として別途つながり、Android の通常再生で鳴るのか
  - それともスマホのスピーカー・イヤホンから鳴らす前提か
- **SDK チームに確認が必要**

## AI 発火

- 「メガネの横をタップ」は `commandManager.gestureEvents`（`SINGLE_TAP` / `DOUBLE_TAP` / `HOLD`）で受ける
- `gestureEvents` は `SharedFlow`。**購読開始前のジェスチャーは受け取れない**
- `要決定` どのジェスチャーに何を割り当てるか（発火・再アライメント・表示切替）

## 実測しないと決められないこと

優先順に：

1. **グラス六軸のヨードリフト率** — アライメントの持続時間が決まる。最重要
2. **`sendImage` 1 枚の転送時間** — 更新レートの上限。追従表示が成立するかが決まる。**サンプルの `ImageScreen` で今すぐ測れる**
3. **六軸データのレイテンシ**（BLE 経由）
4. 屋外・夜間でのスマホ磁気センサーの実誤差
5. **グラスの表示画角**（196x196 が視野の何度を占めるか）— ⑤ の FOV が決まる
