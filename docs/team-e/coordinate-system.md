# 座標変換パイプライン

- ここでは、星表に書かれた数字をグラスの196×196画素のどこに点を打つかに変換するための仕様を決めるドキュメントである
- 星表に載っているのは「シリウスは赤経 6h45m、赤緯 −16.7°」といったデータだが、一方でグラスに出したいのは「画面の (x, y) = (120, 47) に明るい点を打つ」という情報
- この間には次の4種類の基準の違いがある

1. 星表は2000年基準・現在は2026年
2. 地球の自転（同じ星でも時刻で見える方向が変わる）
3. 観測地が違う（鯖江とシドニーでは同じ星が正反対の方向に見える）
4. 頭の向きが違う（同じ空でもどこを向いているかで画面に入るものが変わる）

- **`要決定` `要確認` の付いた項目はまだ決まっていない**

## 全体の構成

```
SABERA ──── 六軸センサ（加速度＋ジャイロ）────→ スマホ
   ↑                                              │
   │                                              │ 日時・時期・位置（GPS）
   │                                              │ 星座データベース
   │                                              │ 磁気センサー
   │                                              │ 方位キャリブレーション
   │                                              ↓
   └──── 画像送信（196x196 グレースケール）──── 天球描画 → 切り抜き

SABERA ──── 横をタップ（gestureEvents）────→ AI 発火 → 音声で解説
```

- **グラスは表示とセンサーに徹し、計算はすべてスマホ側**
- グラスへ送るのは画像のみ

## 変換の全体像

- 変換の全体像は以下の通り

```
星表（ICRS / J2000.0 赤経・赤緯）
        ↓ ① 歳差
of-date の赤道座標 (α, δ)
        ↓ ② 恒星時 — 観測地の経度 + UTC → LST、時角 H = LST − α
時角系
        ↓ ③ 地平座標変換 — 観測地の緯度 φ
地平座標（方位角 A・高度 h）※ 真北基準
        ↓ ④ 姿勢 — グラスの六軸 + 方位オフセット（キャリブレーションで決める）
視線ベクトル
        ↓ ⑤ 投影 — 視線中心の接平面へ
196x196 のスクリーン座標
        ↓ ⑥ ラスタライズ（グレースケール 0-255）
sendImage(width, height, grayscale)   ※ 量子化と圧縮は SDK 0.0.12 が行う
```

- 「星表の座標」と「of-dateの赤道座標」に関しては、1回計算すれば当分変わらない
- 「地平座標」は時刻とともに変わる、「視線ベクトル」への変換は毎フレーム変わる
- この頻度の違いが「行列を毎フレーム組み直さない」という方針につながる

## 実装方針（全段共通）

### 内部表現は単位ベクトルで統一する

- 素直に実装すると、各段を「角度→角度」の変換として書きたくなる（例：赤経赤緯を入れて方位角高度が出てくる関数）
- しかしこれには2つの罠がある
1. 天頂（高度90度）では方位角が定義できない
2. $¥cos{h}$での除算ができない場合がある（特に90度の時）
- **そこで角度ではなく単位ベクトルで持つ**
- このようにすることで、変換がすべて3×3の回転行列の掛け算になる
- ①〜④ がすべて回転行列の積になり、特異点が消える

```
v_screen = R_attitude · R_horizon(φ) · R_hourangle(H) · R_precession · v_catalog
```

- 歳差 = `R_z(−z) · R_y(θ) · R_z(−ζ)`
- 時角 = `R_z(H)`
- 赤道→地平 = 緯度 φ による `R_y`
- 姿勢 = グラスの回転行列（六軸から得る）

- さらに、もう1つの利点として行列を先に掛け合わせておけるという利点がある
- 歳差行列は起動時に1回作ればよく、緯度による行列は場所が変わるまで固定、毎フレーム変わるのは時角と姿勢だけなので、`R_precession` と `R_horizon` は事前に合成して 1 つの行列にしておける
- 5000 個の星を毎フレーム変換するときに重要

### 座標系の規約を 1 箇所に固定する

**符号バグの温床。** 決めて文書に書き、実装では 1 箇所に定数として置く。

| 決めること | 採用（案） | 備考 |
|---|---|---|
| world 座標系 | **ENU**（X=東, Y=北, Z=天頂） | Android の `getRotationMatrix` と同じ。NED と混ぜない |
| 方位角の起点 | **北 = 0°** | 天文の伝統には南起点の流儀もある。混在させない |
| 方位角の向き | **東回り（時計回り）** | Android と同じ |
| 手系 | **右手系** | |
| グラス機体座標 | `要確認` | 加速度・角速度の軸がどちらを向くか。実機で確かめる |

### 時系は UTC で足りる

- `GMST` の式は **UT1** 基準だが、`DUT1` は最大 0.9 秒 = **約 13″**。無視できる
- 歳差の計算は本来 **TT**（TT − UTC ≒ 69 秒）だが、歳差量への影響は無視できる
- → **UTC をそのまま使ってよい。** ただし端末時計のずれは別問題（1 分ずれで 0.25°）

### ユリウス日は D を直接持つ

- `JD ≒ 2,460,000` を Double で持つと仮数部の上位が食われる
- **`D = JD − 2451545.0` を直接計算して保持する。** 大きな数の引き算を避ける

### 日周運動の速さ

- 星は **15″/秒**（1 分で 0.25°、4 分で 1°）
- **画像の更新間隔がこれを超えると、静止して見えない／ずれる**
- 転送時間の実測（後述）と合わせて更新方針を決める

## ① 星表 → of-date

- 地球の自転軸は約26000年周期でコマのように首を振っている
- これにより天の北極の位置が動き、赤経赤緯の原点そのものがゆっくりずれていく
- J2000から2026年までの26年で約0.36度
- これは満月の直径に近い量なので、無視してしまうと星座線が明らかにずれてしまう
- そこで**歳差行列を導入する**
- ここで無視しているのは、オーダーが明らかに小さい以下の3つ
1. **章動**（最大 17″）
2. **固有運動**（26 年で数十″）
3. **光行差**（最大 20″）

## ② 恒星時

- 地球が回っているため、「今どの赤経が南中しているか」が時々刻々と変化する
- これを表すのが恒星時
```
GMST = 18.697375 + 24.065709824279 × D   （時間単位、D = JD − 2451545.0）
```
- 係数が 24 ではなく 24.0657 なのがポイント
- これは恒星日が太陽日より約 4 分短いことを表している（地球は自転しながら公転もしているので、太陽に対して 1 周する間に星に対しては 1 周と少し回る）

- `LST = GMST + 経度 / 15`（東経を正）
- 時角 `H = LST − α`

## ③ 地平座標変換

- 天の北極・天頂・星の3点が作る球面三角形に球面の予言定理を導入する

観測地の緯度 φ、時角 H、赤緯 δ から：

```
sin h = sin φ · sin δ + cos φ · cos δ · cos H
A = atan2( −cos δ · sin H,  sin δ · cos φ − cos δ · sin φ · cos H )
```

- `A` は**真北基準・東回り**
- **大気差** — 高度 0° で約 34′、10° で約 5′、45° で約 1′。地平線近く以外は無視できる

## ④ 姿勢の出所

- **ここから先がデバイス固有の問題**
- **グラスは六軸センサ（加速度＋ジャイロ）。** ここから何が言えるかが設計を決める。

### API（SDK 0.1.0 で解放済み）

```kotlin
fun startImuData()
fun stopImuData()
val imuData: SharedFlow<CommandManager.ImuData>
val imuDataStarted: StateFlow<Boolean>
```

1 サンプルの中身：

| フィールド | 内容 |
|---|---|
| `accelX/Y/ZMilliG` | 加速度 [mg] |
| `gyroX/Y/ZDps` | 角速度 [dps] |
| `pitchDegrees` | ピッチ [度]（融合済み） |
| `yawDegrees` | ヨー [度]（融合済み・**AR 起動基準の相対値**） |
| `timestampMs` | AR 起動からの経過時間 [ms] |

実装上の注意：

- **`startImuData()` を呼ぶまで何も流れない**
- **`timestampMs` で間隔を計る。受信時刻を使わない**（BLE 経由で順序と間隔が乱れる）
- **送信キューが詰まるとグラス側がサンプルを捨てる。** 指定周期どおりには届かない前提で組む
- **ロールは融合値として提供されない。** 3 軸加速度から自前で出す（重力方向が分かるので算出できる）
- ファームは `FEATURE_VERSION 2.0.0` 以上。切断するとグラス側で止まるので再接続後は呼び直す
- サンプル実装は `samples/kmp/app/.../ui/ImuScreen.kt`

### 六軸で取れるもの・取れないもの

| 量 | 可否 | 理由 |
|---|---|---|
| **pitch・roll** | **絶対値が取れる** | 加速度計が重力を測るため |
| **yaw** | **絶対値が取れない** | 磁力計が無く、ヨー方向には基準になる外力が無い |
| 方位の**変化量** | 取れる（ただしドリフトする） | ジャイロの積分 |

- **グラスに磁力計が無い以上、グラスの絶対方位を直接得る手段は存在しない**
- 未知数は **方位オフセット 1 つだけ**
- これをキャリブレーションで決める

### `sendNaviCourse` — グラスに方位を渡す口（SDK 0.1.0 から）

```kotlin
fun sendNaviCourse(courseDegrees: Double)
```

上流の説明はこうなっている。

> 端末の GPS 進行方向を送る。グラスは磁力計を持たず方位を単体で保てないため、
> **この値をジャイロのドリフト補正に使う**。案内中に数秒おきに送る。

**分かったこと＝ファームにヨーの外部補正が入っている。** これは大きい。
引数はただの角度なので、**GPS 進行方向でなくてもよい**。こちらで求めた方位を入れられる。

**しかしキャリブレーションは要らなくならない：**

| 期待 | 実際 |
|---|---|
| これで方位が分かる | **分からない。** 送るのはこちらで、グラスが返すのではない |
| GPS で方位が取れる | **GPS 進行方向は「歩いている向き」で「顔の向き」ではない。** 立ち止まると値が出ない |
| キャリブレーションが不要になる | **`courseDegrees` に入れる値を作る工程がキャリブレーションそのもの** |

- → `sendNaviCourse` は**答えではなく、答えの置き場**
- 「案内中に送る」とあるので、**ナビ状態でないと効かない可能性**がある

**それでも価値がある。`要確認` ここが最重要：**

- **補正後の方位が `imuData` の `yawDegrees` に返ってくるか**
- 返るなら、**ドリフト補正をファームに任せられる**
- こちらは段階 1 の同期で**初期オフセットを 1 回入れるだけ**でよくなり、
  「何分ごとにかざすか」の問題が消える
- 返らない（ナビ表示の内部だけで使う）なら、こちらでドリフトを持ち続ける

**歩いている間だけなら実は使える：**

- 観測地へ歩いて向かう間は、GPS 進行方向 ≒ 顔の向きのことが多い
- そのまま流し込めば、**着いた時点で粗い方位が入っている**状態にできる
- 誤差は大きい（歩きながら首は振るし、低速では GPS 方位が荒れて ±10〜20°）
- **段階 1 の前置きとしては使えるが、これ単体では星座線を重ねる精度に届かない**

### スマホの磁気は「連続では」使えない。ただし同期はできる

- スマホの磁気が示すのは**スマホの方位**であって、**グラスの方位ではない**
- 頭とスマホは独立に動くので、両者の相対姿勢は常には分からない
- → 磁気とジャイロを**常時**相補フィルタで融合する定石は使えない

**しかし、両者の向きを揃える瞬間を 1 回作れば、そこで方位を移せる。**

- スマホを顔の前にかざせば、**そのときだけ**スマホの向き ≒ 視線の向き
- その瞬間の「スマホの磁気方位」と「グラスの `yawDegrees`」の差が方位オフセット
- 以後はグラスのジャイロで追従し、ドリフトしたらまたかざす

→ 詳しくは [方位キャリブレーション設計](#方位キャリブレーション設計)

## 方位キャリブレーション設計

**このアプリの精度を決める中核。**

- 6DoF で**仰角と傾き（pitch / roll）は絶対値が取れている**（加速度計が重力を測るため）
- **未知数は方位オフセット 1 つだけ**
- これをどう埋めるかを、**誰でもできる方法から順に**三段構えで用意する
- **`sendNaviCourse` があってもこの節は不要にならない。** あれは求めた方位の置き場であって、
  求める手段ではない（[前節](#sendnavicourse--グラスに方位を渡す口sdk-010-から)）

### 前提：天体の同定は一般の人には難しい

- 「南南西・高度 30° にベガがあります」と言われても、**方位も高度も星の名前も分からない**のが普通
- 街中では 1 等星すら数個しか見えない
- → **天体アライメントは上級者向けの精度モードであって、標準フローにはできない**

### 段階 1：スマホ同期（標準・誰でもできる・昼夜問わない）

```
1. 「スマホを顔の前にかざして、正面に向けてください」
2. その瞬間、スマホの背面方向 ≒ グラスの視線方向
3. スマホの磁気で得た絶対方位 − グラスの yawDegrees = 方位オフセット
4. 以後はグラスのジャイロで追従する
```

- **星の名前を知らなくてよい。昼でも夜でも、曇っていてもできる**
- 誤差 = 磁気の誤差（±5〜15°）＋ 向きを揃える精度（±10° 程度）
- **`要確認` この精度で星座同定が成立するかは実測して決める**

**再同期が安いのが最大の利点：**

- スマホをかざすだけなので**何度でもやり直せる**
- 天体を探す方式と違い、コストが桁違いに低い
- → **ジャイロのドリフトが速くても運用が成立する。** ドリフト率のリスクをここで吸収できる

### 段階 2：天体アライメント（精度モード）

磁気の誤差を消したいときに使う。**カメラで照準させれば、星の名前を知らなくてよい。**

```
1. スマホのカメラで空を映す
2. 画面中央のレティクルに、明るい天体を入れてタップ
3. アプリはスマホの向き（磁気＋重力）から「そこにあるはずの天体」を逆算して同定する
4. 同定できた天体の真の方位からスマホの方位オフセットが決まる（磁気誤差が消える）
5. 段階 1 の同期でグラスへ移す
```

- **ユーザーは「一番明るい点を枠に入れる」だけ。** 名前も方位も知らなくてよい
- 磁気の粗い方位（±15°）と、重力で正確に取れる高度があれば、**候補はほぼ一意に絞れる**
- グラスで直接天体を見る方式は、視野中心に入れる操作が難しいので上級者向け

### 段階 3：手動微調整

- 校正後に星図を出し、「見えている空と合っていますか」と聞く
- ずれていればジェスチャー（`SINGLE_TAP` / `HOLD`）で回して合わせてもらう
- 段階 1・2 のどちらの後にも使える

### 昼間の扱い

**昼間も使えるようにする。** 星は見えないが、「見えないけれど今この方向にオリオン座がある」を見せる体験は成立する。

| 手段 | 昼 | 夜 |
|---|---|---|
| 段階 1（スマホ同期） | **使える** | 使える |
| 段階 2・太陽で照準 | **使える** | — |
| 段階 2・月で照準 | 使えることがある | 使えることがある |
| 段階 2・恒星で照準 | — | 使える |

**安全上の絶対条件：**

- **グラスの視野中心に太陽を入れさせてはいけない。** 太陽の直視になる
- 太陽を使うなら**スマホのカメラ越し**に限る（画面を見るので直視にならない）
- 太陽の位置計算は簡単で、視差も 8.8″ で無視できる。**基準天体としては最も正確**

**昼間の月も使える：**

- 上弦〜満月は午後、下弦は午前に空にある
- 月を使うなら**地心視差の補正が必須**（最大 57′）

### 精度は本当に足りないのか

- 星座の大きさは **10〜40°**（オリオン座 20°、さそり座 40°）
- **±15° でも「オリオン座はこのあたり」は言える**
- → **まず段階 1 だけで実測し、足りなければ段階 2 を足す**という順序で進める

### 基準天体は低い高度を選ぶ（段階 2 のとき）

**アライメント誤差の伝播を考えると、基準天体の高度が効く。**

- 高度 h の天体では、天球上の角度ずれ δ に対して方位オフセットの誤差は `δ / cos h`
- そのオフセットで高度 h′ を見ると、天球上の誤差は `δ · cos h′ / cos h`
- → **高い天体で校正すると誤差が拡大し、低い天体で校正すると縮小する**

| 校正天体の高度 | 誤差の増幅（`1 / cos h`） |
|---|---|
| 20° | 1.06 倍 |
| 45° | 1.41 倍 |
| 60° | 2.0 倍 |
| 80° | **5.8 倍** |

- 純粋に誤差だけなら**低いほどよい**が、低すぎると大気差（高度 10° で 5′）と地形障害が効く
- **高度 20〜40° の天体を選ぶのが妥当**

### 天体が足りなくなることは無い

段階 2 を夜に使う場合、基準にできる星が year-round であるかを実データで確認した。

東京（35.68°N, 139.77°E）で各月 15 日 21:00 JST に、**高度 20〜50°** にある星の数：

| 月 | 1.5 等以下 | 2.0 等以下 | 2.5 等以下 |
|---|---|---|---|
| 1 | 3 | 7 | 17 |
| 2 | 4 | 13 | 29 |
| 3 | 6 | 17 | 24 |
| 4 | 5 | 11 | 14 |
| 5 | 4 | 7 | 10 |
| 6 | 5 | 7 | 16 |
| 7 | 4 | 7 | 19 |
| 8 | 1 | 4 | 18 |
| 9 | **0** | 2 | 13 |
| 10 | 4 | 6 | 11 |
| 11 | 3 | 7 | 13 |
| 12 | 4 | 10 | 16 |

- **2.5 等まで含めれば、どの月でも 10 個以上**が使える高度にいる
- 9 月だけ 1.5 等以下がゼロになるが、2.5 等まで広げれば 13 個ある
- 昼は太陽が常にあるので、そもそも困らない

### ドリフト率の位置づけ

- MEMS ジャイロのヨードリフトは民生品だと**数°/分**のオーダーになることがある
- ただし**段階 1 の再同期が安いので、致命傷にはならない**
- `要確認` それでも実測はする。「何分ごとにかざす必要があるか」が体験を決める

## ⑤ 投影

- 視線方向を中心とした接平面に投影する
- 中心からの角距離 θ を像面半径 r に写す
- 球面を平面に写す以上、**すべてを保つことは原理的に不可能**。何を諦めるかを選ぶ

### `決定` 投影方式：ステレオ投影

| 方式 | 式 | イメージ | 保つもの |
|---|---|---|---|
| **心射図法（gnomonic / TAN）** | `r = tan θ` | 球の**中心**から光を出して接平面に落とす | **大円が直線になる** |
| **ステレオ投影（stereographic）** | `r = 2 tan(θ/2)` | 球の**反対側の極**から光を出す | **角度と形**（等角写像） |

形の歪み（縦横比の崩れ）を FOV ごとに比べると：

| FOV | gnomonic | stereographic |
|---|---|---|
| 40° | 6.4% | **0%** |
| 60° | 15.5% | **0%** |
| 90° | 41% | **0%** |

- gnomonic の歪みは `sec θ`（半径方向 `sec²θ`、接線方向 `sec θ` の異方性）
- stereographic は等角なので**形の歪みは常にゼロ**。全体のスケールだけ周辺で 3〜7% 変わる

判断材料：

- このアプリは**星座の「形」を見せて同定させる**のが本質 → 等角の stereographic が理屈では有利
- gnomonic の利点「星座線を直線で引ける」は、**円弧を 5° ごとの折れ線に分割すれば数行で済む**ため差は小さい
- 196x196 という解像度では差が視認できない可能性もある
- **決定: stereographic を採用する。**
  - 星座の「形」で同定させるのがアプリの本質なので、等角写像であることを優先した
  - FOV を後から広げても崩れない
  - 星座線は円弧になるが、**5° ごとの折れ線に分割すれば実用上の差は無い**

### `決定` FOV：30〜40°（表示画角が自由な場合）

- 196px に空の何度分を入れるか
- 狭いほど星が大きく描け、広いほど星座と周囲の文脈が入る。

空のサイズの目安：満月 0.5° / こぶし（腕を伸ばして）約 10° / **オリオン座 約 20°** / 北斗七星 約 25° / さそり座 約 40°

| FOV | 解像度 | 5 等まで視野内 | 入るもの |
|---|---|---|---|
| 20° | 9.8 px/度 | 15 個 | オリオン座がぎりぎり。星は大きく描ける |
| **30°** | 6.5 px/度 | 33 個 | 星座 1 つ＋周辺の文脈 |
| **40°** | 4.9 px/度 | 58 個 | 星座 1 つに余裕 |
| 60° | 3.3 px/度 | 129 個 | 星座 2〜3 個。密で潰れ気味 |

**前提が 1 つ未確認：** `要確認` グラスの表示画角（196px が視野の何度を占めるか）

- **視界に重ねる**なら FOV は表示画角に一致させる必要があり、**選ぶ余地がない**
- **参照図として見せる**なら自由に選べる
- **決定: 自由に選べる場合は 30〜40° とする。** オリオン座が画面の半分〜2/3 を占める大きさ
- **ただしグラスの表示画角が判明したら見直す。** 視界に重ねるなら選ぶ余地が無くなる

**パネルが 576×360 と分かって、この制約はきつくなった。**

- 196x196 が等倍で出るなら、**画像の画角はパネルの画角の 196/576 = 34% に固定される**
- 例えばパネルが 34° でも、**画像は約 12°** しかない
- → **視界に重ねる**なら、星図 FOV は 30〜40° ではなくその 34% に縛られる。
  **オリオン座（20°）が画面に収まらない**
- → **参照図として見せる**なら 30〜40° のままでよいが、実際の空とは重ならない
- `要決定` **重ねるのか、参照図なのか。** ここを決めないと FOV は決まらない
- [天球インスペクタ](#ブラウザで確かめる)でパネルの画角と出かたを変えて見比べられる

### `決定` ロール：地平線を水平に固定する

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **追従** | グラスの傾きに合わせて星図も回す | 実際の空と一致する。重ねて見るなら自然 | 星図が常に回って読みにくい。文字を焼くと文字も傾く |
| **固定** | 地平線を常に水平に保つ | 星座早見盤と同じで参照図として読みやすい | 頭を傾けると視界とずれる |

- ロールは重力基準で**絶対値が取れている**ので、**どちらも実装できる**。純粋に体験の判断
- **決定: 地平線を水平に固定する。** 196x196 の小さな窓に出す以上、AR オーバーレイより参照図としての性格が強いため、読みやすさを優先した
- **ロールは 6DoF の融合値には無いので、3 軸加速度から自前で算出する**（重力方向が分かるので出せる）
- 投影段のパラメータにしておき、実機で重なり具合を見てから追従に切り替えられるようにする

## ⑥ ラスタライズ

出力先は `sendImage`。**SDK 0.0.12 で簡素化され、取り込み済み。**

```kotlin
fun sendImage(width: Int, height: Int, grayscale: ByteArray)
```

- 渡すのは **1 画素 1 バイトのグレースケール**（0-255、左上から行優先、長さは `width * height` 以上）
- **3bit への量子化と RLE 圧縮は SDK が行う。エンコーダを自前で書く必要はない**
- サイズ上限は **196x196**。超えるとファーム側で弾かれ、何も表示されない
- **表示面は緑の単色。** 渡すのはグレースケールだが、映るのは**緑の 8 階調**
  - API の契約はグレースケールのままなので、**緑の値を作って渡すのではない**
  - 設計するときは「緑 8 段でどう見えるか」で考える
- `samples/kmp/app/.../GlassImage.kt` に流用できるものがある
  - `Bitmap.toGlassGrayscale()` — 縦横比を保って 196 に縮小し、輝度だけ取り出す
  - `testPatternImage()` — 画像を用意せず送信を試せるテストパターン
- `samples/kmp/app/.../ImageScreen.kt` に送信画面のサンプルがある。**転送時間の実測はここから始められる**

残る設計判断：

- `要決定` 星の等級の表現。**緑の 8 階調**しかなく、**量子化は SDK が行うので制御できない**。明るさだけでは潰れるので、点の大きさ（1px / 2px / 3px）との組み合わせを検討する
  - [天球インスペクタ](#ブラウザで確かめる)で、限界等級と FOV を変えたときの潰れ具合を目で確かめられる
- 描くのは 0-255 のグレースケールでよいので、**Android の Canvas でそのまま描いて `toGlassGrayscale()` に通す**のが素直
- `要決定` 星座線を描くか、線の階調をどうするか
- `要決定` 星座名を画像に焼くか、テキストとして出すか（**画像とテキストは同時に出せない**。画面ごと切り替わる）

### 表示パネルは 576×360（SDK 0.2.0 で判明）

- 0.2.0 の自由配置キャンバス（`sendCanvas`）が **576×360 の座標**で要素を置く
- → **画像表示ページの 196x196 はパネルの一部でしかない**。等倍なら幅の 34%・高さの 54%
- `要確認` 196x196 が拡大して出るのか等倍で出るのか、パネルのどこに出るのかは実機未確認
- **画素数が分かっても画角は分からない。** 「196px が視野の何度か」は依然として未確認のまま

### `sendCanvas` で星座名ラベルを置ける（SDK 0.2.0 で追加）

```kotlin
fun sendCanvas(elements: List<CommandManager.CanvasElement>)   // 全消しして置き直す
fun sendCanvasElements(elements: List<CommandManager.CanvasElement>)  // 差分更新
```

- `CanvasElement(id, x, y, width, height, text)` — **置けるのはテキストだけ。画像は置けない**
- **576×360 の任意座標に置ける**ので、「視野内のこの位置に、この星座名」という出し方ができる
- id は **0..7 の 8 個まで**、テキスト合計 **190 バイト**まで、`FEATURE_VERSION 2.1.0` 以上

→ **星図（画像）を出さずにラベルだけ出す経路が成立する。** ここは投影の出口が
196x196 ではなく 576×360 になるだけで、**④ までの計算はそのまま使える**。

**ラベル方式は方位誤差に強い。**

- 星図を重ねると、5° ずれれば線が明らかに合わない
- ラベルは「その方向に名前が浮かぶ」だけなので、**多少ずれても破綻しない**
- → **キャリブレーションの精度要求が下がる**。段階 1 だけで成立する可能性が高いのはこちら
- `要決定` 星図とラベルのどちらを主にするか。**画像とテキストは同時に出せない**ので択一

## ⑦ いま見ている星座を決める

**`決定` 視野中心が属する星座を、IAU の星座境界で判定する。**

星座を「近さ」で選ぼうとすると壊れる。理由：

- 星座の広がりを実データで測ると、**うみへび座 95°・エリダヌス座 66°** に対して**こいぬ座・や座は 4〜5°**
- **重心までの距離**で測ると、うみへび座の重心は誰も見ていない空白にあるので、
  アルファルドを見ていても他の星座に負ける
- L 字・S 字の星座では重心が図形の外に出る

視野内から選ぶ方式も成立しない：

| FOV | 視野内の星座数（平均） | 最大 | 1 個以下 |
|---|---|---|---|
| 30° | 3.5 | 9 | 2% |
| 40° | **5.2** | 11 | **0%** |

- **FOV 40° では星座が 1 個だけの視野が空のどこにも無い**
- 「視野内で最大」にすると**エリダヌス座・おおぐま座・うみへび座**が常に勝つ。
  視野いっぱいのオリオン座を見ていても、はみ出した巨大星座に負ける
- → **視野内は「候補集合」であって選択ルールにならない**

**IAU 境界は天球を隙間なく 88 分割している**ので、任意の 1 点が属する星座は一意に決まる。
距離もしきい値もチューニング項目も無く、引き分けも起きない。

### 実装の選択肢

| 方法 | 中身 | 評価 |
|---|---|---|
| **Roman (1987) の境界表** | 357 行の赤経・赤緯の帯。`astropy.get_constellation` の中身 | **第一候補。**自己完結で軽い |
| d3-celestial の `constellations.borders.json` | 47 KB・J2000 に歳差済み | **閉じた多角形ではなく隣接ペアの境界線**（257 本、`ids: "And,Lac"`）。描画向き |

- Roman 表は **B1875 系**なので、of-date → B1875 の歳差が要る（① の行列を逆に使う）
- 境界線データは**判定には組み立て直しが要る**が、**境界を描きたくなったらそのまま使える**

### 中心方式の弱点と手当て

**視野中心が星の無い場所を指すことがある。** 実データで数えた値：

| 限界等級 | 中心から最寄りの星まで（中央値） | 8° 超 | 12° 超 | 最悪 |
|---|---|---|---|---|
| 3 等 | 7.6° | 47% | 20% | 22° |
| 4 等 | 4.4° | 11% | 2% | 16° |

- 3 等までしか見えない街中では、**空の 20% で「中心の周り 12° に何も無い」**
- → 中心から一定角内に表示中の星が無ければ、**正直にそう言う**
  （「うみへび座のあたりですが、この方向に明るい星はありません」）
- 視野内で最も明るい星の所属星座に譲る手もあるが、**フォールバックであって主ルールにしない**

### ラッチとヒステリシス

- **ツルをタップすると頭が動く。** タップ時点の姿勢を使うと反動でずれた方向を判定してしまう
- → **タップ直前 0.5 秒ほどのラッチ値**から判定する
- 併せて、**境界から一定角（キャリブレーション誤差より大きめ）内側に入り、
  かつ一定時間維持されたときだけ切り替える**
- 包含判定なら「境界から何度内側か」が自然に出るので、**距離方式よりヒステリシスが書きやすい**
- `要決定` 内側マージンと保持時間の具体値。実機で決める

## 星座データベース

- 夜空の下=電波が悪い場所で使うためオフラインで完結させる
- そのため、外部 API は不要でアプリに同梱する。

### 候補（取得と検証を済ませたもの）

**[d3-celestial](https://github.com/ofrohn/d3-celestial)（BSD-3-Clause）が第一候補。**

| ファイル | サイズ | 中身 |
|---|---|---|
| `data/stars.6.json` | 641 KB | 6 等までの恒星 **5,044 個** |
| `data/constellations.lines.json` | 26 KB | 星座線。**89 グループ / 150 本の折れ線 / 893 頂点** |
| `data/starnames.json` | 664 KB | 固有名・バイエル符号など（必要なら） |

- 形式は **GeoJSON**。`id` は **Hipparcos 番号**、`properties` に `mag`（実視等級）と `bv`（B−V 色指数）
- 元期は **J2000 を実測で確認済み**（シリウス 0.7″、ポラリス 1.8″ の差＝丸め誤差の範囲）
- 出典は XHIP（Extended Hipparcos Compilation）ほか。VizieR 由来

**座標の持ち方に注意：**

- 座標は `[lon, lat]` で、**`lon` は −180〜180 に折り返されている**（赤経ではない）
- 赤経に戻すには `RA = lon < 0 ? lon + 360 : lon`
- `lat` はそのまま赤緯

- `tools/simulator/index.html` をブラウザで開くだけ。ビルドもサーバーも要らない
- 同梱の星表を、この仕様どおり（歳差 → 恒星時 → 地平座標 → ステレオ投影 → 196x196）に描く
- **グラスに映る緑単色 8 階調まで再現している**
- **表示パネル（576×360）を点線、画像表示ページ（196x196）を実線**で描き分けている
- 196x196 が**等倍で出る場合と拡大される場合**を切り替えて見比べられる

確かめられること：

| 見たいこと | 操作 |
|---|---|
| 限界等級と FOV の組み合わせで潰れないか | スライダーを動かす |
| 歳差を入れる価値があるか | チェックを外すと 0.36° のずれが出る |
| 季節・時刻・観測地で何が見えるか | 日時と観測地を変える |
| 星座の形がステレオ投影で保たれるか | 星座を選んで視野を移す |

座標変換は独立に検算済み。鯖江でポラリスが方位 0.83°・高度 35.64°（緯度 35.94°）に来るが、
これは**ポラリスが実際に天の北極から約 0.7° 離れている**ためで、期待どおりの値。

## 実測しないと決められないこと

優先順に：

1. **段階 1（スマホ同期）だけで星座同定が成立するか** — 成立するなら精度モードは後回しにできる。最重要
2. **グラス六軸のヨードリフト率** — 「何分ごとにかざす必要があるか」が決まる
3. **`sendImage` 1 枚の転送時間** — 更新レートの上限。追従表示が成立するかが決まる。**サンプルの `ImageScreen` で今すぐ測れる**
4. **六軸データのレイテンシとサンプル落ち**（BLE 経由）— **サンプルの `ImuScreen` で今すぐ測れる**
5. 屋外でのスマホ磁気センサーの実誤差
6. **グラスの表示画角**（パネルが視野の何度を占めるか）— ⑤ の FOV が決まる
7. **グラス機体座標の軸定義** — 加速度・角速度の各軸がどちらを向くか
8. **手元のファームの `FEATURE_VERSION`** — 6DoF は 2.0.0、キャンバスは **2.1.0** 以上が要る。
   6DoF が動いてもキャンバスは動かないことがある
