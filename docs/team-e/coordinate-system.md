# 座標変換パイプライン

- 星表の座標から、グラスに出す 196x196 の画像上の位置までをどう変換するかの仕様
- **議論の叩き台。`要決定` の付いた項目はまだ決まっていない**

## 全体像

```
星表（ICRS / J2000.0 赤経・赤緯）
        ↓ ① 歳差（章動・固有運動は要検討）
of-date の赤道座標 (α, δ)
        ↓ ② 恒星時 — 観測地の経度 + UTC → LST、時角 H = LST − α
時角系
        ↓ ③ 地平座標変換 — 観測地の緯度 φ
地平座標（方位角 A・高度 h）※ 真北基準
        ↓ ④ 端末姿勢 — Android ROTATION_VECTOR（磁北基準）+ 磁気偏角補正
端末座標系（視線ベクトル）
        ↓ ⑤ 投影 — 視線中心の接平面へ
196x196 のスクリーン座標
        ↓ ⑥ ラスタライズ + 3bit グレースケール + RLE
sendImage(width, height, encodedBitmap)
```

## ① 星表 → of-date

- 星表は ICRS / J2000.0 元期で配布されるものが多い
- **歳差** — J2000 から 2026 年で約 0.36°。星座同定の精度要求（`要決定`）次第では省略可
- **章動** — 最大約 17″。星座同定には効かない。省略してよい
- **固有運動** — 明るい星でも年 1″ 未満。26 年で最大 数十″。省略してよい
- **年周視差・光行差** — 光行差は最大 20″。省略してよい

`要決定` 歳差を入れるか。入れるなら簡易回転行列（ζ, θ, z）で足りる。

## ② 恒星時

- `GMST = 18.697375 + 24.065709824279 × D`（時間単位、D = JD − 2451545.0）
- `LST = GMST + 経度 / 15`（東経を正）
- 時角 `H = LST − α`
- 端末時刻は NTP ずれがありうるが、1 分ずれても 0.25° なので実用上問題ない

## ③ 地平座標変換

観測地の緯度 φ、時角 H、赤緯 δ から：

```
sin h = sin φ · sin δ + cos φ · cos δ · cos H
A = atan2( −cos δ · sin H,  sin δ · cos φ − cos δ · sin φ · cos H )
```

- `A` は**真北基準・東回り**
- **大気差** — 高度 0° で約 34′、10° で約 5′、45° で約 1′。地平線近く以外は無視できる
- `要決定` 大気差を入れるか。星座同定なら不要、地平線付近の見え方を正しくしたいなら入れる

## ④ 端末姿勢

- Android の `SensorManager.getRotationMatrixFromVector()` で `TYPE_ROTATION_VECTOR` から回転行列を得る
- 得られる world 座標系は **ENU**（X = 東, Y = 北, Z = 天頂）
- **`ROTATION_VECTOR` の Y 軸は磁北**。真北に直すため `GeomagneticField.getDeclination()` で偏角を補正する（日本では西偏 7〜9° 程度）
- 端末の持ち方は `SensorManager.remapCoordinateSystem()` で吸収する

### 最大の誤差源は磁気コンパス

- 磁気センサーの方位精度は環境次第で **±5〜15°**
- 上流の変換をどれだけ厳密にしても、ここが支配的
- `要決定` 対策をどうするか
  - 何もしない（星座を大づかみに示すだけなら許容できるかもしれない）
  - ユーザー補正 — ジェスチャー（`SINGLE_TAP` / `HOLD`）で表示を回転させて合わせてもらう
  - 明るい星でアライメント — 見えている 1 等星を指定してもらい、そこを基準にオフセットを決める
  - `TYPE_GAME_ROTATION_VECTOR`（磁気を使わない）でドリフトを抑え、初期方位だけ磁気で決める

### グラスの姿勢は取れない

- SDK 0.0.11 に**グラスの IMU 値を読む API は無い**（`enterImuDebugPage()` はページを開くだけ）
- したがって「グラスが向いている方向」は**原理的に分からない**
- 取れるのは**スマホの姿勢**だけ

`要決定` 何を「かざす」のか。ここが仕様の根幹。

| 案 | 内容 | 座標系への影響 |
|---|---|---|
| A. スマホをかざす | スマホを空に向け、グラスは結果の表示器に徹する | 姿勢の不一致が起きない。**変換が閉じる** |
| B. 頭の向きを推定 | グラスの向き ≒ スマホの向きと仮定 | スマホをポケットに入れた瞬間に破綻する |
| C. キャリブレーション | 一度両者を同じ方向に向けて基準を取る | 頭を動かすたびにずれる。補正手段が無い |

## ⑤ 投影

- 視線方向を中心とした接平面に投影する
- `要決定` 投影方式
  - **gnomonic (TAN)** — 大円が直線になる。視野が広いと周辺が大きく歪む
  - **stereographic (STG)** — 等角。**星座の"形"が保たれる**ので、形を見せる用途に向く
- `要決定` 画角（FOV）
  - 196x196 に何度分を入れるか
  - 星座 1 つを収めるなら 30〜40°程度が目安（オリオン座で約 20°）
  - 広くすると star hopping しやすいが、1 星あたりの画素が減る

## ⑥ ラスタライズ

- 出力は **196x196 以下**。超えるとファーム側で弾かれ、何も表示されない
- **3bit グレースケール（8 階調）を RLE 圧縮**。エンコードは呼び出し側で実装する
- `要決定` 星の等級をどう表現するか
  - 8 階調しかないので、明るさだけで等級を出すと潰れる
  - 点の大きさ（1px / 2px / 3px）と明るさの組み合わせが現実的か
- `要決定` 星座線を描くか、線の階調をどうするか
- `要決定` 星座名の文字を画像に焼くか、テキストとして別ページに出すか
- RLE 圧縮は横方向のランが長いほど効く。**背景が黒（0）で疎な星図は圧縮が効きやすい**

## 未検証

- `sendImage` は **team-e の誰もまだ実機で試していない**
- 1 枚あたりの転送時間（BLE の帯域）が分からないため、**更新レートの上限が不明**
- リアルタイムに追従させられるのか、静止画を都度更新するのかは実測してから決める
