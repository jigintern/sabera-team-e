# グラス出力の制約

グラスに何をどれだけ出せるか。**星座モードと衛星モードで共通の土台**なので、
他の文書はここを参照する。

## 表示面

| 項目 | 値 |
|---|---|
| パネル | **576×360**（キャンバスの座標系。左上が原点） |
| 画像 1 枚 | **544×340 を試して、入らなければ 528×330**（16:10。バッファ上限から決まる） |
| 階調 | **緑の 8 階調**（3bit）。API に渡すのはグレースケール 0-255 |
| 黒 | **透明**（波導ディスプレイ。光る画素だけが肉眼の空を邪魔する） |
| スピーカー | **無い**（ハードとして存在しない。音はスマホから鳴らす） |

**画角は未確認。** 画素数が分かっても視野の何度を占めるかは別問題。

## 使う API

```kotlin
fun sendCanvasImage(id: Int, x: Int, y: Int, width: Int, height: Int, grayscale: ByteArray)
fun sendCanvasElements(elements: List<CommandManager.CanvasElement>)   // 差分更新
fun sendCanvas(elements: List<CommandManager.CanvasElement>)           // 全消去して並べ直す
fun removeCanvasImage(id: Int) / clearCanvas() / closeCanvas()
```

- **送るだけで画面が切り替わる。** 先にページを開かなくてよい
- **テキストは画像の手前に描かれる。** 星図とラベルが同じ画面に共存できる
- 同じ id に送ると座標ごと差し替わるので、星図は **id 固定の 1 枚**でよい
- 終わるときは `closeCanvas()` か `enterHomePage()`。送らないと星図が出たまま残る
- **リモコンの戻る操作でキャンバスは閉じられる。** 0.5.0 でリスナーが撤去されたので
  閉じられたことに気づけない。**いつでも送り直せる作りにする**

## 上限

### 画像（バッファ 380,000 バイト）

SDK が `IllegalArgumentException` で弾く条件（0.6.0 のソースで確定）：

| 条件 | |
|---|---|
| `0 <= id < 8` | 8 枚まで |
| `x >= 0` / `y >= 0` / `width > 0` / `height > 0` | |
| `x + width <= 576` / `y + height <= 360` | |
| **`width * height * 2 + 圧縮後サイズ <= 380,000`** | **置いてある全画像の合計** |

- **枚数より先にバッファが尽きる。** 設計は枚数ではなく**面積**で考える
- **576×360 は画素だけで 414,720 になり 1 枚でも入らない**（実機で確認）
- 16:10 の上限は **544×340（369,920）**。圧縮後に残るのは **10,080 バイト**で、
  背景の下限（面積 / 32 = 5,780）を引くと**星と線と絵に使えるのは 4,300 バイト**しかない
- **入るかどうかは空の濃さと向きで変わる**ので、送る前に同じ式で数えて、
  溢れたら **528×330（348,480・圧縮後に 23,899 バイト）** へ落とす。
  設定を変えるとまた上限から試す
- 圧縮は **1 バイトに `(値3bit shl 5) or (連長 - 1)`**、連長 32 まで。
  **同じ数え方をすれば送る前に上限を判定できる**
- **ナビ表示中は使えない**（全体ルート画像とバッファを共有）
- **天体案内中は 528×330 の星図と、軸に沿った細長い案内表示を重ねる。**
  枠は左右の矢印 **120×56**・上下の矢印 **56×120**・到着の輪 **80×80**。
  画素ぶんは矢印で合計 361,920 バイト、輪で 361,280 バイト。
  圧縮後サイズも足して送信前に 380,000 バイト以内か検査する
- **枠を形に合わせるほど、同じバッファで長く描ける。** `width * height * 2` がそのまま効くので、
  同じ 13,440 バイトを正方形（82×82）に使うと矢印は 72px、**120×56 なら 105px** になる。
  矢印は必ず軸に沿うので、正方形では短辺のぶんが丸ごと無駄
- **これ以上大きくできない。** 星図の圧縮後に残るのは 17,000 バイトほどで、
  背景の下限だけで 5,445 バイト（面積 ÷ 32）。**溢れると星図ごと送られない**ので、
  そのときは**矢印を外して星図を通す**（文字の案内は残る）

### テキスト（8 要素・190 バイト）

- `CanvasElement(id, x, y, width, height, text)`。**id 0..7 の 8 個・合計 190 バイト程度**
- はみ出した矩形は端で切られ、外に出た要素は描かれない
- `sendCanvasElements` は差分更新。**空文字を送るとその id が消える**
- 矩形は文字数から取る（120×22 では「みなみのかんむり座」が切れて読めなかった）
- 星座名は平均 **14.8 バイト**なので 8 個で約 118 バイト。
  FOV 40° の視野に入る星座は**平均 5.2 個・最大 11 個**で、**8 枠はちょうど足りる**
- **190 バイトは 1 電文あたりの上限であると同時に、画面に置ける合計でもある**（#40 で判明）。
  分割して送ると**先に置いたぶんが押し出されて消える**ので、
  枠は**数（8）とバイト数（190）の両方**で打ち切る（`GlassCanvas.toCanvasElements`）。
  数だけで詰めていたときは、日本語の名前 8 個で 200 バイトを超え、
  **先頭の枠＝案内のラベルから消えていた**
- 名前 1 個は 12 バイト＋文字ぶんなので、**日本語 5 文字なら 27 バイト・7 個で頭打ち**。
  入らない名前は飛ばして次を見る（並びは優先順位なので、余ったバイトへ短い名前が入る）

### 文字だけのページ（解説画面・#40）

星図の画像を消すと、枠 8 つを全部文字に使える。

**8 行ぶん置いたら、実機で最初の 1〜2 行が消えて途中から始まった**（2026-08-22）。
190 バイトは 1 電文あたりの上限だと読んでいたが、**画面に置ける合計でもある**らしく、
分割して送っても後から送ったぶんに押し出される。そこで**字幕のように 1 行ずつ流す**。

| | 値 |
|---|---|
| 1 行 | **17 文字**（画素の見積り 19 文字と 1 電文 190 バイトの**小さいほう**。画素側は未実測） |
| 1 枚 | **3 行・189 バイト・1 電文**。1 枚目は見出し＋本文 2 行（34 文字）、2 枚目からは本文 3 行（**51 文字**） |
| 行数 | パネルには 8 行入る（40px × 8 = 320）が、**1 枚に置けるのは 3 行** |
| 転送 | 1 枚 190 バイトで**1 電文・10ms ほど**。星図画像 1 枚の 1/30 |

- **1 行の文字数は画素と電文の小さいほうで決める。** 画素の見積り（`LABEL_CHAR_WIDTH = 28`）だけで
  19 文字にしていたときは、日本語で埋まった 3 行が **207 バイトで 2 電文に割れ**、
  **後から送ったぶんに先の行が押し出されて解説が全部出なかった**。
  電文側（190 ÷ 3 行）で 17 文字に切る。**画素側は未実測**で、数えたら定数 1 つを直せばよい
- **行を増やしても入る文字は増えない。** 要素 1 つに座標と大きさで 12 バイトかかるので、
  行を 1 本増やすたびに本文へ回せるバイトが減る（3 行なら 17 文字、4 行なら 11 文字、5 行なら 8 文字）。
  **日本語で 8 文字の行は語の途中で折れて読めない**ので、3 行で止める
- **増やせるのは見出しを畳んだぶんだけ。** 見出しを出したままだと本文は 2 行 34 文字で、
  一度に目に入る量が少なすぎた。**見出しは 1 枚目だけ**にして、2 枚目からは 3 行すべてを本文に使う
  （星座名は 1 枚目と読み上げの頭で伝わっている）
- **同じ行は同じ場所に置き、行を組み直さない。** 組み直すとファームが前の行の末尾を残す（「る」問題）
- **見出しが空でも本文を繰り上げない**（1 枚ずつ組む側）。名前が付いた瞬間に本文が 1 行下がって
  全部書き直しになる。**流し始めるときの畳み込みは 1 回だけ**なので、これとはぶつからない

**安いので 1 文届くたびに描き足せる。** 画像でやると 1 更新 332〜390ms かかって成立しない。
流す速さと見せ方は [画面遷移とジェスチャー](05_app-flow.md)。

## 転送量と時間

実機（528×330・5 等・星座線あり）で測った圧縮後サイズは **6,000〜7,500 バイト**。

| 中身 | バイト |
|---|---|
| 真っ黒な背景の下限（面積 / 32） | 5,445 |
| 星と星座線 | 600〜2,000 |

- **8 割が背景の下限。** 面積を変えない限り転送量は減らない（星座線を切っても 1 割）
- 送るのは 200 バイトずつ。**1 本あたり実測 8〜9ms**（`PACKET_MS_DEFAULT` の定数）。
  528×330・圧縮後 6.1〜6.7KB を 12 回送って**実測 332〜390ms**だった（Pixel 9a、2026-08-20）
  - もとの見積り 20ms/本 は**倍以上の過大**で、そのぶん次の絵を無駄に待っていた
  - **転送中も 6DoF は流れ続ける**ため完了検出には使わない。実測値から 10ms/本で見積もり、
    最後に描画待ち 200ms を置く
- **0.6.0 で SDK が分割送信を直列化した。** 続けて送ってもチャンクは混ざらない。
  ただし呼び出しは積むだけで返るので、**転送が追いつかないと古いフレームが順番待ちで残る**
- **マイクを流すと毎秒 32,000 バイトが同じ BLE を通る**ので、星図の転送と食い合う
- `cancelPendingPackets()` で積んだフレームを捨てられそうだが `要確認`

## 描き直しの条件 —「首が止まったら 1 枚」

**転送中、グラスは前の絵を捨てて何も出さない。** 528×330 は実測 332〜390msで、
アプリは最後に描画待ち 200ms を置く。連続で送ると表示時間より消えている時間が長くなるため、
首が止まったときだけ送る。

| 条件 | 値 |
|---|---|
| 「動いている」とみなす角速度 | 0.1 秒で 1° 以上 |
| 止まったと判断するまで | **0.18 秒** |
| 送り直すずれ | **前に送った絵から 6° 以上** |
| 転送の見積り | **9ms / パケット**（実測 8〜9ms の上端） |
| 描き終わりを待つ余裕 | **80ms** |

**止めてから出るまでが体感の速さ**で、上の 4 つがそのまま足し算になる。
0.4 秒＋10ms／パケット＋200ms から詰めた（合計でおよそ 0.3 秒ぶん早い）。
**短くしすぎると首を動かしている途中で送り始めて、転送のあいだ真っ暗になる回数が増える。**

### 止まりきる手前で「止まる先」へ 1 枚（`alignment/HeadMotion.kt`・**実機未確認**）

上の足し算をこれ以上詰めても、**転送の 0.4 秒は残る**。止まってから送り始める限り、
止めてから絵が出るまで 0.5 秒以上はグラスが暗い。

そこで**完全に止まるのを待たず、減速に入った時点で 1 枚だけ先出しする**。
人の首は急に止まらないので、**転送が終わるころの視線**を外挿してそこ向きの絵を焼く。
送る枚数もバイト数も増えないまま、絵が出るのが 0.2〜0.4 秒早くなる（**実機で未確認**）。

| | 値 |
|---|---|
| 減速とみなす条件 | 窓（0.3 秒）の**後半が前半の 0.7 倍より遅い** |
| 外挿する先 | **転送見積り ＋ 80ms** 後の視線 |
| 割引 | **0.6**。行き過ぎるより届かないほうが安全 |
| 外挿の頭打ち | **8°**（画角 35° の 1/4） |
| 先出しの間隔 | **1.2 秒**。振り続けている間に何枚も送ると点滅になる |

- **速さは cos(高度) を掛けた球面上の角度で測る。** 天頂付近では方位が少し振れるだけで大きく動く
- **足りない分は次の描き直しが埋める。** 行き過ぎた絵は「合っていない星図」として残る
- **「なめらかに動かす」ではない。** 1 回の首振りに対して出る絵は先出しの 1 枚と、
  止まったあとの補正 1 枚まで

- **姿勢が動かなくても更新は要る。** 星は日周運動で **15″/秒**（4 分で 1°）動く
- **画像を送ってから名前を送る。** 逆順だと転送中に名前だけが先に浮く
- 名前は差分更新なので毎フレーム送ってよい。**余った id は空文字で消す**
- **全画面を「なめらかに動かす」のは原理的に無理。** 星図は首が止まったときだけ送り直す。

### 天体案内の表示（#46・#61）

**2026-08-24 の実機で「矢印が非常に分かりにくい」。** 直したのは 3 点で、
理由は [落とし穴](11_pitfalls.md) にも入れた。

| | 前 | いま |
|---|---|---|
| 形 | 細線のシェブロン＋2〜4px の点 3 つ | **塗った軸＋塗った三角の頭** |
| 階調 | 90 / 150 / 220 / 255（3bit の 2・4・6・7 段目） | **最上段だけ**（255） |
| 枠 | 64×64 の正方形 | **軸に沿った 120×56**（上下は 56×120） |
| 文字 | 「オリオン座 案内中」だけ | **2 行目に「左へ 32°」** |

- 星図とは別の**画像 id 1** をパネル中央へ固定し、6DoF に近い速さで差し替える
- **細線と中間の階調で描かない。** 波導ディスプレイの黒は透明なので、
  暗い画素は屋外の空に負ける。**2〜4px の点は背後の星と見分けが付かない**（星図も点で星を描く）
- **頭は軸の 3 倍以上ひらく**（軸 13px に対して頭 45px 幅・22px 長）。
  最初に描いた 145°・0.20 では頭が軸より 5px 広いだけで、**棒に瘤が付いた形**にしかならなかった
- **枠が変わるときは先に消す**（`GuidanceOverlaySender`）。
  左右・上下・到着で大きさも位置も違うので、同じ id へ重ねると前の枠がはみ出したまま残る
- **矢印と同じことを文字でも言う。** テキストは 2.1.0 のファームでも出た唯一の経路で、
  画像より先に信用できる（下のファーム要件）。1 行目は対象名、
  **2 行目は「いまの段で詰める差」**（`StarMap.guidanceTurnText`）。
  角距離ではなく左右差・上下差なので、**首を振ると減る＝案内が自分を追えていると分かる**
- **斜めの案内は出さない。** 最初は左か右だけを示し、左右差5°以内で上か下だけへ替える。
  上下を合わせている途中で左右差が8°を超えたら、左右の矢印へ戻す
- 左右・上下は水平を保った空の接平面で分け、首を傾けるロールとは混ぜない
- 対象以外の星座線・星座絵を薄くし、周囲の星座名と結びの名前は一時的に隠す
- 10°以内では矢印を**短く**する。**細くはしない**（近づくほど見えにくくなっては案内にならない）
- 5°以内を0.5秒保つと**中央の星＋二重リング**へ替える。輪も 5px の帯で描く
- 到着時の対象線・対象点は全画面の次の1枚へ焼き込む。全画面を10Hzでは送らない
- 小画像の転送中も `sendGate` を共有し、星図・字幕・明るさの送信と重ねない。
  **差し替えの周期を追従の見張り（100ms）と同じにしない**（[落とし穴](11_pitfalls.md)）

## ファーム要件と退路

| 出すもの | 必要な `FEATURE_VERSION` | 2.1.0 台の実機での結果 |
|---|---|---|
| 分割レイアウト（`sendLayout`） | 2.0.0 | — |
| キャンバスのテキスト（`sendCanvas`） | 2.1.0 | 出た |
| **キャンバスの画像（`sendCanvasImage`）** | **2.2.0** | **出なかった** |
| `enterImageDisplayPage` ＋ `sendImage`（196×196） | 要件なし | 出た |

- SDK チームからは「使える」と聞いていたが**実機が追いついていなかった**。
  伝聞で確定させず送って確かめる価値があった
- **設計上の退路（アプリ未実装） = `enterImageDisplayPage` ＋ `sendImage`。**
  196×196 で星図だけなら古いファームでも出せる
- **`FEATURE_VERSION` の読み出し経路が不明**なので、切り替えの判定方法は未決定

## 夜空で使うためのグラス設定

`sendSetting(name, value)` でグラス本体の設定を書き換えられる。キー一覧は上流ドキュメントに無く、
`sources.jar` の `CommandManager.SettingKey`（17 個）から読み取ったもの。

| キー | なぜ効くか |
|---|---|
| `BRIGHTNESS_LEVEL` / `BRIGHTNESS_AUTO` | **暗順応。** 明るいまま出すと肉眼の空が見えなくなる |
| `SCREEN_OFF_TIME` | **見上げたまま何分も止まる**使い方。途中で消えると成立しない |
| `MESSAGE_DISPLAY_MODE` / `NOTIF_CONTENT_MASK` | **通知が出ると星図が消える**（同時には出せない） |
| `FONT_SIZE` | 星座名の大きさ＝入る文字数が変わる |
| `FEATURE_VERSION` | ファームの機能バージョン（読み出し経路が不明） |

### 明るさ設定

- `BRIGHTNESS_LEVEL` は **0..4 の5段階で、大きいほど明るい**。
  [team-f の実機調査](https://github.com/jigintern/sabera-team-f/pull/11)では、0..4 は受理され、
  5以上はエラーなしで拒否された。同じ設定キーと電文を使う
  [公開実装](https://github.com/itcayman/XinCaiGlass/blob/89b472cea9b8f4ff36e8466155cb996a31256182/entry/src/main/ets/core/config/GeneralConfig.ets)
  とも一致する
- `BRIGHTNESS_AUTO = true` の間は手動の明るさが無効になる。
  **アプリでは自動調整を使わず、手動値を送る前に必ず false を送る**
- team-f の実機では、設定値は**次の画面再描画で見た目へ反映**された。team-e でも設定送信後に
  最後に表示したキャンバス画像を同じ id へ送り直す。キャンバスでの反映は **team-e 実機確認待ち**
- SDK 0.6.0 自体は値域を検査しないため、アプリ側で 0..4 に制限する
- SDK は設定同期のパース結果を公開していない。設定画面に出せるのは本体の現在値ではなく、
  **このアプリが最後に送った値**だけ
- 設定画面は手動5段階のスライダーだけにする。段階が変わると `BRIGHTNESS_AUTO = false` を送り、
  100ms 待ってから最新の `BRIGHTNESS_LEVEL` を送る。その後、直前の星図画像を再送する
- ドラッグ中の段階をBLEへ積まないよう200msまとめ、画像送信中は他の描画と排他にする

- `sendWakeupTiltThreshold(degrees)` は**見上げでグラスが起きるしきい値**。
  星を見る姿勢と正面衝突するが、噛み合わせれば「空を見上げた瞬間に星図が出る」入り口になる
- `requestSystemStatus()` で**バッテリー・装着状態・充電状態**を要求できる。
  装着状態が取れれば外している間の送信を止められるが、**応答は `parseResponse` 経由で経路が不明**

## 実測しないと決められないこと

優先順に：

1. **パネルが視野の何度を占めるか** — FOV が決まる
2. **200 バイト 1 パケットの実時間** — 描き直しの間隔が決まる
3. **屋外での適正な明るさ** — 0..4 の各段階を昼・薄明・夜で実測する
4. **ラベルの読みやすさ** — 8 個並べて重ならないか、緑 8 階調で読めるか
